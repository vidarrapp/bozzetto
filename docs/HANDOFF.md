## Notes for Bozzetto Studio

### Unit vertex normals, and the mirrored dab picked after the dab (2026-11-01)

Found by running Clay on the Bozzetto core alongside this engine (M2-8, bozzetto-web scripts/core-clay.mjs), and decided by Vidar the same day: the engine matches the core.

- **Vertex normals are unit length**: the faces' area-weighted sum, normalised (vendor `Mesh.js` `updateVerticesNormal`). Upstream divided the sum by the number of faces, which left the area around the vertex in the length; every sum of normals (the plane fits) weighed vertices by it. On the parity fixtures this moves the brushes that sum normals: on the cube (a unit across) Clay by 64% of its move, Surface smooth by 64%, the rake by 11%; on the sphere in centimetres Clay by 0.3%, Polish by 9%; Drag, Move, Pinch, Smooth's average and the paint brushes not at all. Synthesis normalises before it builds a frame, so the details of saved scenes decode as before.
- **The ring is updated**: `updateGeometry` recomputes the normals of every vertex of the faces that changed (and marks them dirty for drawing), not only of the vertices moved; a vertex just outside a dab kept a stale normal before, up to 1.4 apart from its faces' on a sculpted sphere.
- **Saved normals are made unit as a scene opens** (they are still restored, for their direction), and the scale bake no longer multiplies them by the scale squared.
- **The mirrored dab is picked after the dab** (vendor `SculptBase.makeStroke`): the dab first, then the mirrored side picked on the surface it left, as upstream did only under dynamic topology. Where the two sides overlap near the plane of symmetry they saw different surfaces before.

With these, the core and the engine agree on Clay to 0.00001 cm, mirrored strokes included. Fixtures recorded before carry the old normals.


### The .bozz poly group layout, version 2 (2026-11-01)

Bozzetto Web writes poly groups per object as an optional field of the object record, `meshes[i].groups`, with a version of its own; the scene's `v` stays 4. Since 2026-11-01 (Vidar's call) the groups are stored on the LOWEST level, level 0 (the base mesh, `baseFaces`). A scene without the field opens with every face in group 0, named "Group 1". The web writes the field only when an object has groups worth keeping (more than one group, group 0 renamed, something hidden, or a colour picked), so a file from an object that was never grouped is byte-for-byte what it was before.

```
groups: {
  v: 2,
  faces: Uint32Array,   // one a face of LEVEL 0, in baseFaces order (length nbBaseFaces), each an index into names
  names: string[],      // 1 to 4096 names, each at most 200 characters; group 0 is "Group 1" until renamed
  hidden?: Uint8Array,  // one a group (names.length), 1 = hidden; left out when nothing is hidden
  colors?: Uint32Array  // one a group (names.length): 0xRRGGBB (sRGB) picked for it, or 0xFFFFFFFF for its default hue; left out when no group has a colour of its own
}
```

- **Level.** Only level 0 is stored, whatever `sel` is and however many levels there are: `faces.length` must equal `nbBaseFaces`, and `faces[i]` is the group of base face `i` (`baseFaces[4i .. 4i+3]`).
- **Higher levels inherit exactly.** Face `f` of a level has its children at `4f .. 4f+3` of the level above, triangles and quads alike (vendored SculptGL `editing/Subdivision.js`, `applyOddSmooth`, writes them there in face order). For a quad `(v1 v2 v3 v4)` child `4f+k` is the quad at corner `v(k+1)`: `(v1 m1 c m4)`, `(m1 v2 m2 c)`, `(c m2 v3 m3)`, `(m4 c m3 v4)`, `m` the edge midpoints and `c` the centre. For a triangle `(v1 v2 v3)` child `4f` is the middle triangle `(m1 m2 m3)` and `4f+1 .. 4f+3` the corner triangles at `v1`, `v2`, `v3`. So face `f` at level `k` belongs to level-0 face `floor(f / 4^k)` and takes its group, with no vote. Subdividing and deleting the highest level change nothing stored. A scene's higher levels are rebuilt by subdividing `baseFaces`, so in a file this numbering always holds.
- **Rounding to level 0 (the one rule both apps must share; changed 2026-11-01).** When a group is made at a higher level (Ctrl+W from a mask drawn there, the loop mask then Ctrl+W), the faces on screen that qualify (every corner masked, hidden faces not) are rounded down BY SHARE: a level-0 face joins the new group when MORE than half of its faces on the level on screen qualify; exactly half stays out. The level-by-level vote of 2026-11-01's first build (each face of the level below taking what most of its four children have, the earliest child on a two-two tie) is dropped: which child is earliest turns with each base face's corner order, so a loop drawn across the middle of a row of base faces split the row unevenly (24 of 32 in on the default sphere), and the owner saw the uneven border. By share, a loop drawn along base-face edges is followed exactly and one drawn between them goes to the nearest base-face loop, the whole row alike. Groups made on level 0 itself are the qualifying faces as they are. With several groups in play (version 1 conversion, Rebuild) the majority rule still runs on group numbers level by level: a face takes the group most of its four children have, the earliest child's on a tie among the tied groups.
- **By angle** works on level 0's own faces: each level-0 face's normal is the area-weighted sum of its faces' normals on the level on screen (the surface as sculpted, not level 0's stale vertices), and level 0 is split where two neighbouring base faces' normals are more than the angle apart, each connected piece a group, numbered by its first base face. (A split of the level on screen rounded down level by level was tried and dropped: on a subdivided figure it gave one group at 40 degrees, where level 0 gives the cage's creases.) Studio may split any way it likes; the result stored is per base face either way.
- **Rebuild.** Rebuild (the vendor's reversion) puts a new level 0 under the old one; each new base face takes the group most of its four children (old level-0 faces) have, the earliest child on a tie. In the session the old level 0 keeps its own face order, which need not be `4f .. 4f+3` of the new one, so the web reads each child's parent off the reversion (a coarse quad's centre vertex, a coarse triangle's middle child and its three edge neighbours); once saved and reopened the stack is subdivided from the new base and the contiguous numbering holds again. A Delete lowest (not in the web's UI) would make level 1 the base, each face its old parent's group.
- **Other topology.** Dynamic-topology, voxel-remeshed, quad-remeshed and merged objects have one level, so their faces are level 0. Dynamic topology on: each triangle takes the group of the face on screen it came from (a quad's two triangles both); off: the static faces keep the dynamic faces' groups in order. Voxel remesh, quad remesh, merge and extract: each new face takes the group of the nearest old face centre (world space) on the level on screen; merge unites names by name. Duplicate, mirror and radial copies carry the groups; a mirror copy rewinds its base faces but keeps their order, so the groups go along unchanged.
- **Colours (2026-11-01).** A group shows its default hue until a colour is picked for it: hue `(0.08 + g * 0.618033988749895) mod 1`, saturation 0.55, value 0.92, taken as LINEAR RGB for the display (polyGroups.ts `groupColor`). A picked colour is stored as `0xRRGGBB` in sRGB, as a colour picker gives it, and drawn converted to linear; `0xFFFFFFFF` means the default hue. `colors` is optional and the record stays at version 2: a reader that does not know it (the web before 2026-11-01, whose sanitiser keeps known fields only, and whose `checkHeader` ignores fields it does not check) opens the file with the default hues. A colour belongs to its group, not its number: it goes with the group through a rename, a delete, Remove unused, a split into objects, a merge (names united by name, the first source's colour for a name), copies and remeshes. When a delete or a renumbering moves a group that still has its default hue to another number, the web stores the hue it showed as that group's colour (`0xRRGGBB` of the hue at its old number), so what shows on screen does not change; the field is written from then on. Groups made anew (By angle, Auto, Clear all, an OBJ's lines, Visible's new group) start on the default.
- **The container.** `hidden` brings a third buffer kind to the `.bozz` buffers table, `t: 'u8'`: `len` counts bytes, the array still starts on a multiple of four in the blob region, and the region's size is each entry's `off + len * (t === 'u8' ? 1 : 4)`. `f32` and `u32` are as before. A reader without `u8` refuses only files that hide something.
- **OBJ.** On import, each file face is in the group the last `g` or `o` line before it names (the rest of the line, "default" when empty; a face before any such line in "Group 1"), groups numbered by first use; the file's faces are level 0, so the groups go straight in. The numbered export writes the file back unchanged while every face's group name is still the one its own `g`/`o` lines give; otherwise it drops the file's `g` lines (keeping `o`, `usemtl`, `s`, `mtllib`) and writes `g <name>` before each face that starts another group, each file face taking its level-0 face's group; a file face that became several level-0 faces (a pentagon is a quad and a triangle) takes the majority of theirs, the earliest on a tie. The triangle export writes `g <name>` lines face by face at the level on screen when the object has groups.
- **Checks.** The web (shared/bozz.ts `checkHeader`, the app's sanitiser, the server's content check) takes version 2 with `faces` a u32 array of `nbBaseFaces`, and still takes version 1 sized to the top level; it refuses any other version or size, names that are not 1 to 4096 strings of at most 200 characters, a `hidden` that is not a u8 array of one a name, a `colors` that is not a u32 array of one a name (the app also refuses a value that is neither at most `0xFFFFFF` nor `0xFFFFFFFF`), or (the app, which reads the arrays) a face naming a group past the last. The web always writes version 2.

**Version 1 (2026-10-31, one day of use).** `v: 1` stored one group a face of the TOP level (`faces.length` = `nbBaseFaces * 4^(levels.length - 1)`, in the order full subdivision produces) and derived lower levels by the majority rule above. The web reads it by rounding the top level down to level 0 level by level with that rule (each face the group most of its four children have, the earliest child on a tie), and saves it back as version 2. A build from 2026-10-31 refuses a version 2 file as a version it does not read.
